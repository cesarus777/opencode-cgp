# Chart failure and recovery

Date: 2026-11-07. Status: implemented; see the [delivery report](../validation/chart-failure-recovery-2026-11-07.md) for validation and limitations. Covers UX-10 from the [TUI UX review](tui-ux-review.md), following delivered UX-01 through UX-09. The investigation, design targets, and sequence below record the implementation scope.

## Recommendation

Implement accurate retained-history failure states and recovery. Before this increment, a temporary chart read failure told native-panel users that their server needed history support, and manual retry cleared an otherwise usable chart. Users should see what failed, whether the displayed chart is from an earlier read, and what retry actually does.

This increment covers performance Charts in the native panel and History in the standalone dashboard. Preserve the delivered compact layouts, terminology, help, selection, existing keys, and read-only monitoring. The sidebar and Details context chart use bounded local context traces rather than history RPC; they do not need this failure treatment. Standalone Models has a separate analytics service and remains outside this increment.

## Investigation and baseline

Findings are from repository source, the installed pinned SDK, and offline tests. No new interactive host session, remote-server check, or user study was performed for this plan.

## Error and display contract

Use a small renderer-independent history failure contract, proposed in `src/historyclient.ts`, with approved reason values and fixed copy. It may inspect structured error codes and abort signals; it must never parse arbitrary server message text or expose messages, response bodies, URLs, credentials, stacks, or content.

| Condition                                                  | Primary wording / action                                                                                                                                | Automatic native polling                                                                                    |
| ---------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------- |
| First read                                                 | `Loading retained history…`                                                                                                                             | One read in flight.                                                                                         |
| Refresh with matching results                              | `Updating history · showing previous results`                                                                                                           | Keep chart and original range while loading.                                                                |
| Valid result                                               | Existing chart/retention notices.                                                                                                                       | Continue existing five-second cadence.                                                                      |
| `enabled: false`                                           | `History recording is disabled in this server location.` Explain that retry checks again after configuration changes.                                   | Pause until explicit retry or remount.                                                                      |
| Valid empty result                                         | `No retained measurements in this window.`                                                                                                              | Continue polling; new measurements may arrive.                                                              |
| `rpc.unavailable` or `rpc.method_not_found`                | `History service is unavailable in this server location. Check that the owning server has a plugin version with chart history. Press r to check again.` | Pause until explicit retry or query remount/change. Do not claim an upgrade is certainly required.          |
| Deadline expires                                           | `History request timed out. Press r to retry.`                                                                                                          | Continue at the existing cadence; do not overlap reads.                                                     |
| Invalid schema, wrong-session series, `rpc.invalid_output` | `History response is incompatible. Check client/server plugin versions. Press r to retry.`                                                              | Pause until explicit retry or query remount/change.                                                         |
| `rpc.invalid_input`                                        | `History request was rejected. Check client/server plugin versions. Press r to retry.`                                                                  | Pause until explicit retry or query remount/change.                                                         |
| Network, busy/internal, authorization, or unknown failure  | `History could not be loaded. Press r to retry.`                                                                                                        | Continue at the existing cadence. Do not guess authentication or service-busy causes from generic failures. |
| Superseded selection/window/location, help, or close       | No error from the canceled read.                                                                                                                        | Abort and dispose the obsolete task/timer.                                                                  |

On a failed refresh with a matching successful result, append `Showing previous results · last loaded <UTC timestamp>` before the chart. Use the locally recorded successful receipt time, and retain the response's original `from`/`to` separately. An initial failure has no stale-result claim or empty chart axes. A successful retry clears the error/stale warning atomically with the new result and range. A disabled response replaces old plotted results rather than leaving them visible as current history.

These copy targets must fit through existing cell-aware wrapping. Keep retry and stale status before chart content; preserve essential footer controls at narrow widths. Do not imply that refreshing history changes Guard enforcement or completes compaction.

## Query identity, retention, and concurrency

The retention key includes owning server/client scope, resolved location, full session ID, and window duration. Metric selection and width only reformat the retained response and issue no reads. Each successful read also stores its actual range and receipt time. A new query clears the previous query's chart and error immediately; no cross-session, cross-location, or cross-window fallback is allowed.

At this increment, native retention was local to the mounted Charts component, with one matching result. A stable resolved location identity from native state made a location change invalidate that result even when the session ID stayed unchanged. No native multi-query cache or persisted chart data was introduced. Help/close discarded the local retained result, and returning to Charts loaded again. The later [chart-help continuity increment](native-chart-help-continuity.md) moves that one-result state to the panel so help retains it; closing the panel still discards it. Preserve the dashboard's existing 16-entry bounded cache and immutable projections.

Separate native query changes from manual refresh triggers. A manual refresh marks the matching result as updating and starts or queues the newest read; rapid `r` presses coalesce without parallel history calls. Keep a generation token and query-key check on every settlement, including errors and finalizers, so late success/failure cannot overwrite a newer query. Cleanup aborts active work and clears polling. Distinguish user/navigation cancellation from the five-second deadline, which is a visible timeout. Preserve dashboard serialization and generation checks while adding reason state; an obsolete request must not reset the current query's reason or loading state.

Do not add retries inside RPC adapters. Native polling remains bounded by the current five-second cadence and deadline. Standalone keeps its existing controller refresh cadence (30 seconds by default) and `r` behavior, including rechecking paused/unavailable capability. This increment does not introduce a permanent unsupported-capability cache or a new reconnect mechanism.

## Implementation sequence

1. Add the normalized failure type/classifier and fixed status formatter. In `src/tui/state.ts` and `src/dashboard/connection.ts`, preserve approved failure reasons, validate history output/session identity, and distinguish timeout from canceled ownership. Prove behavior with actual SDK-shaped error fixtures, following the existing analytics network fixture.
2. Extract native history request state into a small testable controller (proposed `src/tui/historystate.ts`), with injected reader, clock, and timer ports. Implement one-result retention, query resets, refresh coalescing, polling rules, and generation-checked cleanup. Wire `HistoryCharts` to that controller without changing panel keys or monitor consumer ownership.
3. Extend `DashboardHistory` and the existing controller with an optional approved failure reason and successful receipt time. Keep `unavailable` as the failed-read status with a reason, avoiding another competing status model. Extend stale projection to cover retained results on all failed-read reasons. Render shared readable status text in both surfaces; maintain gap, provenance, retention, and exact-sample inspection behavior.
4. Extend offline state, connection, controller, terminal, and native renderer fixtures. Then extend the existing synthetic-provider proxy/PTY harness to inject missing RPC, one transient failure, and a delayed read, followed by recovery. Keep test-only controls isolated from production paths.
5. Update README chart guidance, `docs/configuration.md`, `docs/testing.md`, and compatibility wording to match delivered behavior. Write a dated validation report, link it here, and mark UX-10 delivered in the review only after acceptance evidence exists.

The first reviewable code increment is normalized errors and boundary tests; helper-only delivery does not complete UX-10. No history RPC schema, archive format, server scheduler, policy, telemetry, dependencies, exports, release, or publication changes are planned.

## Acceptance and verification

- Initial loading, ready, empty, disabled, missing service, timeout, invalid response, rejected request, generic failure, and recovery have distinct and accurate presentation. Unknown failures never assert missing server support. Test both structured missing-method codes and generic HTTP 404/503; HTTP status alone is not capability evidence.
- After success followed by failed background/manual refresh, the native chart remains visible and explicitly stale with its original range and receipt time. Retry success removes the warning. Initial failure has no retained-results label. Verify the existing standalone equivalent with each approved reason.
- Switching session, window, or owning location immediately removes mismatched results and errors. Reject a response containing foreign-session series. Delayed success and delayed failure from an obsolete query cannot alter current state, including after A → B → A navigation.
- Repeated `r` and timer ticks produce no concurrent native reads or unbounded queue. Disabled/missing/incompatible/rejected states pause native polling; explicit retry performs a new read and can recover. Empty results continue polling. Metric/resize changes perform no reads.
- Help, close, route change, and disposal abort obsolete work and leave no polling timers. A timeout is visible; navigation cancellation is silent. Preserve the panel's single monitor consumer and all existing selection/help controls.
- Native and standalone fixtures cover 80×24, 40×20, and 20×12. Check status-before-chart ordering, cell bounds, scrolling to complete remedies, and keyboard retry without losing identity. Inject a private-message canary and verify no rendered text, projected view, or added diagnostics exposes it.
- Run focused tests for the new helper/state and existing history boundaries/renderers, then `bun run format:check`, `bun run typecheck`, and `bun test`. For delivered UI integration, run synthetic-provider native and standalone PTYs on available supported OpenCode 2.0.29/2.1.2 hosts, recording each host and failure scenario actually exercised. Report missing host/runtime access and skipped live checks separately from passes; offline fault injection does not certify remote or real-provider behavior.

Remaining implementation risk is chiefly native effect lifetime: refresh currently recreates the polling effect, and help destroys its component. Validate the extracted controller and actual Solid mount/unmount behavior together. Existing server/client APIs suffice; no new public integration API is needed.

## Delivery notes

The implementation uses the proposed shared failure boundary and native `HistoryState` controller. Native polling uses a single five-second timer after read settlement rather than a permanently running interval; paused states have no polling timer. Refreshes coalesce behind an active read, and every obsolete settlement is generation checked. Native Charts now puts **r refresh** first in the secondary footer so it remains visible at narrow widths. Standalone history keeps its existing queue/cache/status model, with an approved failure reason and successful receipt time added to the projection. Its formatter suppresses plotted/sample output for disabled recording and suppresses misleading empty-data text on initial failure.

The synthetic-provider harnesses inject missing history registration, one HTTP 503 failure, and a delayed read, then verify retained-result labels and successful retry. The standalone harness counts history calls by RPC URL as well as body and accounts for periodic inventory refresh when evaluating navigation. See the delivery report for measured results; the original baseline above is not delivery validation.
